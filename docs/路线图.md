# 开发进度与后续规划

> 状态截至：2026-09-04

## 1. 产品主链路

Arrive 将信息传递拆成三个边界清晰的阶段：

```text
表达者的内在思考
        ↓
   编码 Encoding          ← 当前开发重点
        ↓
共享语义表示 Semantic Packet
        ↓
   传递 Transmission      ← 先定义数据契约与完整性
        ↓
   解码 Decoding          ← 编码稳定后开发
        ↓
接收者能够进入的表达与理解
```

- **编码**回答“表达者究竟想传递什么”；
- **传递**回答“这份含义如何在通道中保持完整、可追溯”；
- **解码**回答“怎样按照具体接收者的知识、语言和思路，使其准确理解”。

当前不把三个阶段同时做深。先让编码结果稳定、忠实且可验证，再开发接收者侧的解码能力。

这是语义职责的分层，不强制规定软件的部署顺序。如果解码运行在接收者一侧，可以先传递 `SemanticPacket` 再解码；如果由发送侧服务代为生成接收者适配文本，则先调用解码模块生成沟通表示，再通过物理通道发送。两种实现都必须保持解码结果可追溯到同一个编码版本。

## 3. 当前主线：编码闭环

### 3.1 编码结果契约

下一阶段首先定义稳定的 `SemanticPacket`（暂定名）。它至少包含：

- 原始素材引用及需要保留的原话；
- 表达者确认的命题；
- 关键概念的个人含义；
- 可追溯的共享语义锚点；
- 个人含义与共享含义之间的差异；
- 支持、因果、条件、冲突和例外关系；
- 事实、推测、未知项和置信状态；
- 表达目的、边界和不得进入输出的内容；
- 编码版本、确认状态和时间。

编码产物不直接针对某一个接收者措辞。它先形成相对稳定的共同语义层，供后续传递和多种解码方式复用。

### 3.2 共享语义锚点

“大家统一认可的解释”在工程上表示**尽可能使用可追溯的共享语义**，而不是宣称所有人只有一种解释。共享锚点可以来自：

- 标准、法律定义或权威术语；
- 有可靠来源支持的领域共识；
- 特定社群或专业语境中的稳定用法；
- 日常语言中的稳定常用含义；
- 对争议概念并列保存的多种主要解释。

这些类别不是固定优先级。系统先依据当前领域、语境、表达目的和适用人群选择候选，再比较来源可靠性、时效性和解释覆盖范围。法律定义只在相应法域和法律语境中具有特殊权重，不能自动覆盖日常或个人语境。

每个锚点记录定义、来源、适用范围、版本、获取时间和共识状态。表达者自己的特殊含义作为“个人语义差异”独立保存，不冒充共享锚点。找不到真实共识时必须明确标记，不用流畅措辞制造虚假统一。

### 3.3 编码循环

```text
原始输入
  → 分段与类型标注
  → 镜像确认
  → 概念澄清
  → 命题与关系建模
  → 连接共享语义锚点
  → 标出个人语义差异
  → 表达者校准
  → 冻结一个编码版本
```

模型只能提出候选编码。未经表达者确认的归纳、关系和概念映射不能冒充最终含义。

### 3.4 编码验收指标

- **忠实度**：表达者是否仍然认得；
- **覆盖度**：重要素材、矛盾和边界是否遗漏；
- **可追溯性**：每个命题和解释能否回到来源；
- **共享可解释性**：陌生读者能否依据语义锚点理解关键概念；
- **差异透明度**：个人用法与常用含义是否分开；
- **不确定性诚实度**：未知和争议是否被保留；
- **版本稳定性**：修改是否通过新版本发生，而非静默覆盖。

## 4. 里程碑

### 里程碑 0：领域与安全基础——已完成首版

- [x] 稳定编号、来源归属和时间化观点；
- [x] 追加式观点回应与任意时间快照；
- [x] 可保留矛盾的思考地图；
- [x] 软件与真实数据物理隔离；
- [x] 数据边界测试、本地提交检查和 CI。

### 里程碑 1：编码数据模型——下一步

- [ ] 定义编码任务、语义单元、概念、关系和编码版本；
- [ ] 定义共享语义锚点及来源、范围和共识状态；
- [ ] 定义个人语义差异；
- [ ] 增加 Alembic 迁移、领域校验和 API 测试；
- [ ] 输出第一版 `SemanticPacket` JSON Schema。

### 里程碑 2：人工可完成的编码闭环

- [ ] 支持自由输入到分段素材；
- [ ] 支持候选命题、概念和关系的逐项确认；
- [ ] 支持矛盾、未知项和禁止输出边界；
- [ ] 支持编码版本对比、冻结与重新打开；
- [ ] 用至少 10 次真实但不入 Git 的样本验证。

### 里程碑 3：模型辅助编码

- [ ] 接入可替换的模型适配层；
- [ ] 保存提示版本、模型版本、输入引用和候选结果；
- [ ] 自动提出澄清问题和共享语义候选；
- [ ] 评估模型是否篡改、遗漏或过度确定；
- [ ] 保证模型不能绕过表达者确认。

### 里程碑 4：传递层

- [ ] 将冻结的编码版本封装为可传递信息包；
- [ ] 保存版本、来源、语境、隐私和完整性哈希；
- [ ] 定义序列化、通道、送达与完整性边界，不在本层做接收者适配；
- [ ] 支持明确授权后的导出，不直接把私人数据发布到软件仓库。

### 里程碑 5：接收者解码——后续开发

- [ ] 建立基于明确资料和可校准假设的接收者模型；
- [ ] 记录接收者的已知背景、概念习惯和推理顺序；
- [ ] 将共享语义映射到接收者更容易进入的词汇、例子和结构；
- [ ] 生成不同接收者的解码候选版本；
- [ ] 通过复述测试、误解检测和真实反馈校准解码结果；
- [ ] 不依据单方素材诊断或臆测接收者心理。

### 里程碑 6：端到端反馈闭环

- [ ] 比较发送前预测与接收后的真实理解；
- [ ] 区分失真来自编码、传递还是解码；
- [ ] 用反馈改进语义锚点和策略，但不改写历史记录；
- [ ] 建立跨时间、跨接收者的表达回顾。

## 5. 近期开发顺序

1. 为 `SemanticPacket` 编写 JSON Schema 和只含合成内容的示例；
2. 设计编码任务、语义单元、共享语义锚点与版本实体；
3. 实现“素材 → 候选编码 → 使用者确认 → 冻结版本”的后端纵向切片；
4. 增加编码忠实度、追溯性和不确定性测试；
5. 再决定模型接入方式；
6. 编码闭环稳定后进入传递层，解码层排在其后。
