# 软件与数据隔离规范

## 1. 目的

Arrive 会处理原话、经历、关系、阅读回应和仍在形成中的判断。把这些内容放进 Git，即使仓库暂时私有，也会产生长期、可复制且难以彻底撤回的历史。因此项目采用硬边界：**GitHub 管理软件、项目框架、指导方法和公共研究资料；项目内由 Git 整体忽略的 `arrive-data/` 管理用户个人数据与运行数据，也允许外部数据根。**

这不是只针对“高敏感材料”的例外规则，而是所有真实用户数据（包括开发者亲自测试的数据）的默认规则。公共文献不是个人数据；但个人阅读批注、共鸣、立场和测试记录仍是个人数据，不因所读文献公开而自动公开。

## 2. 两类资产

### 可以进入软件仓库

- 程序源码、数据库迁移和基础设施配置；
- 自动化测试及完全虚构、不可反推出真实使用者的测试夹具；
- 通用机制、字段定义、协议和架构说明；
- 项目的设计理由、指导方法、公共竞品分析和研究文献索引，以及不含个人数据的原创摘要与方法评述；
- 已核实允许再分发的第三方文献副本，须保留署名、原始链接、版本、许可和修改说明；
- 不含实例内容的空白模板；
- 面向软件本身的发布记录。

### 不得进入 Git 跟踪

- 使用者提供的原话、语音转写、附件和经历；
- 个人资料库中的来源档案、阅读摘要、个人命题和使用者回应；公共研究文献应独立整理为项目资料，不直接复制个人来源卡；
- 澄清问答、关键词出现、个人含义版本、语义确认、协作者归纳、推测、思考地图和冲突记录；
- 模型输入、提示实例、模型输出、评估反馈和运行日志；
- 候选结构、草稿、改写版本、校准记录和最终个人作品；
- 个人思考协作中的决定时间线；不含个人数据的产品设计决定及方法演进说明可以公开；
- SQLite、PostgreSQL 导出、向量索引、缓存、临时导出和备份；
- 任何能与真实个人、关系或一次具体思考过程重新关联的派生数据。

`privacy: shareable` 只表示内容具备被分享的候选资格，**不构成提交到软件仓库的授权**。公开作品需要一次独立、明确的发布操作，并进入专门的发布目的地，而不是 Arrive 软件仓库。

### 公共研究区

项目研究统一放在 `docs/research/`，使用独立的 `REF-NNNN` 编号，不复用个人实例的 `SRC`、`M`、`RSP` 编号或个人数据路径。记录书目信息、公开链接、版本、查阅日期、原创摘要、对机制的启发、证据局限与版权状态；不包含谁读过、个人认同强度或测试经历。

“公开可读”与“允许重新上传全文”分别核查。未确认再分发许可时，仅提交书目信息、原始链接、原创摘要和必要短摘；允许再分发时才在 `docs/research/papers/` 内置副本并附许可说明。项目自身许可证不覆盖第三方文献。涉及个人信息与研究材料混合的文件，重新整理公共版本，不能整包搬入仓库。

## 3. 物理布局

Emotion 是项目总目录，软件结构与数据在其下分目录存放：

```text
D:\emotion\                  # 项目总目录，也是 Git 工作树
├── backend/                 # 后端软件
├── frontend/                # 前端软件
├── docs/                    # 规范与公共研究
├── templates/
├── scripts/
├── .gitignore               # 包含 /arrive-data/
└── arrive-data/             # 全目录不进入 Git
    ├── .arrive-data-root
    ├── .gitignore           # 忽略全部内容
    ├── raw/
    ├── materials/
    ├── sources/
    ├── mirrors/
    ├── semantics/
    ├── responses/
    ├── thought-maps/
    ├── drafts/
    ├── decisions/
    ├── outputs/
    ├── database/
    └── exports/
```

数据根必须满足：

1. 默认使用项目根下的 `arrive-data/`，根 `.gitignore` 整体忽略，且 Git 索引中没有该目录内容；也允许通过 `ARRIVE_DATA_DIR` 指定外部数据根；
2. 不等于或包含项目根；项目内仅允许专用的 `arrive-data/`，不得将源码目录作为数据根；
3. 不通过符号链接、目录联接或挂载点逃逸数据根或连接回软件目录；
4. 自带 `.arrive-data-root` 标识和默认忽略全部内容的 `.gitignore`，不自行初始化为 Git 仓库；
5. 云同步、共享和备份作为单独决定，不因存储在本机而自动开启。

本机默认数据路径为 `D:\emotion\arrive-data`。项目目录归属与 Git 跟踪范围是两件事：数据属于 Emotion 项目，但不随代码提交。

## 4. 写入规则

所有接收用户个人内容和运行数据的接口和任务都必须先取得数据根，再在数据根内构造路径。默认数据根由项目根定位到 `arrive-data/`；业务写入必须通过数据根构造路径，不能散落到当前工作目录或源码目录。公共研究文档由维护者审阅后更新，不成为运行时写入用户数据的替代入口。

SQLite 默认路径为：

```text
${ARRIVE_DATA_DIR}/database/arrive.db
```

显式设置 `ARRIVE_DATABASE_URL` 时同样执行边界校验；应用 SQLite 文件必须解析到 `ARRIVE_DATA_DIR/database/` 内，落在数据根的 database/ 之外都会被拒绝。SQLite URI 文件名不被接受，避免路径解析与实际打开目标不一致。内存数据库和位于仓库外的测试临时目录不受底层测试引擎限制。

应用只会自动初始化不存在或为空的数据目录，写入 `.arrive-data-root` 标识及忽略全部内容的 `.gitignore`，并创建原始、加工、输出、导出、日志与缓存等分类目录。已有合法数据根只补齐缺项，不覆盖已有内容。已有内容但没有正确标识、位于其他 Git 工作树内、项目内数据目录未被忽略或已被跟踪、或管理目录通过链接逃逸的数据根会被拒绝。

未来新增文件存储、模型运行记录、搜索索引或附件处理时，必须在访问前调用 `arrive.config.data_path(data_dir, key)`，只使用允许分类下的相对键；拒绝绝对路径、父目录穿越和链接逃逸，缓存也必须位于数据根内。该检查防止配置和路径错误，不承诺对抗其他本机进程并发替换链接、挂载或硬链接的攻击。备份、加密及远程模型的数据流向是独立问题。

测试在导入应用前即切换到系统临时数据根，不使用开发者环境里的个人数据库；每个测试仍使用独立临时数据库。当前已实现的加工结果保存在数据根内的数据库；分类目录的创建不意味着未来各文件处理模块已经实现。

## 5. Git 防线

边界采用多层防护：

1. 根 `.gitignore` 整体忽略 `/arrive-data/`、历史运行目录、数据库和本机环境文件；
2. `scripts/check_data_boundary.py` 检查 Git 索引的软件路径白名单、专用数据目录的忽略状态、其他违规运行目录、SQLite 文件签名、实例记录 frontmatter 和 `ARRIVE_DATA_DIR`；
3. `.githooks/pre-commit` 在本地提交前执行检查；
4. GitHub Actions 在 push 和 pull request 上重复检查；
5. 后端允许被 Git 忽略且未跟踪的 `arrive-data/`，拒绝源码目录作为数据根，SQLite 仍限定在数据根的 `database/` 内。

本地克隆后执行一次：

```powershell
git config core.hooksPath .githooks
```

这些技术措施不能识别任意文件中的全部语义。提交者仍需按第 2 节判断内容性质；不确定时一律按数据处理，先放在 Git 忽略的数据根。

## 6. 导出与发布

从私人数据生成可分享内容时，采用“导出而非搬回”原则：

1. 明确接收者、媒介、范围和隐私等级；
2. 从数据根生成一个待审阅导出；
3. 完成人工隐私、事实、署名和版权检查；
4. 获得一次针对该版本和该目的地的明确确认；
5. 发布到指定渠道，并在数据根记录发布事件。

一次发布授权不自动适用于后续版本、其他渠道或软件仓库。

## 7. 备份与删除

Git 不是数据备份方案。数据备份应使用单独位置，并根据内容敏感度采用设备加密或加密归档；备份的保留、恢复和删除策略与软件版本管理分开。

删除软件仓库当前版本中的文件不会删除 Git 历史。若数据曾被提交，需要先净化当前树，再经过明确授权执行历史重写和强制推送，并审计远端分支、标签、既有克隆和托管平台缓存。即使重写成功，也不能承诺已复制的数据从所有位置立即消失。

## 8. 评审清单

每次提交前确认：

- 文件是否属于软件、通用方法或经过隐私与版权检查的公共研究资料；
- 测试内容是否完全虚构；
- URL、标题和摘要是否属于公共研究，还是暴露个人阅读、立场或经历；是否混入个人原话与时间线；
- 内置第三方全文是否有可核实的再分发许可、署名与版本记录；
- 是否包含数据库、日志、缓存、导出或模型运行结果；
- 是否把 `shareable` 错当成 GitHub 授权；
- `python scripts/check_data_boundary.py` 是否通过。

任一项不确定，就不提交，并把内容移动到 `ARRIVE_DATA_DIR`。
