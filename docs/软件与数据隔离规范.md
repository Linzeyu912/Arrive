# 软件与数据隔离规范

## 1. 目的

Arrive 会处理原话、经历、关系、阅读回应和仍在形成中的判断。把这些内容放进 Git，即使仓库暂时私有，也会产生长期、可复制且难以彻底撤回的历史。因此项目采用硬边界：**GitHub 管理软件，仓库外目录管理真实数据。**

这不是只针对“高敏感材料”的例外规则，而是所有真实使用数据的默认规则。

## 2. 两类资产

### 可以进入软件仓库

- 程序源码、数据库迁移和基础设施配置；
- 自动化测试及完全虚构、不可反推出真实使用者的测试夹具；
- 通用机制、字段定义、协议和架构说明；
- 不含实例内容的空白模板；
- 面向软件本身的发布记录。

### 不得进入软件仓库

- 使用者提供的原话、语音转写、附件和经历；
- 第三方全文、来源卡、来源摘要、摘录、命题和使用者回应；
- 澄清问答、协作者归纳、推测、思考地图和冲突记录；
- 模型输入、提示实例、模型输出、评估反馈和运行日志；
- 候选结构、草稿、改写版本、校准记录和最终个人作品；
- 从真实协作产生的决定时间线；
- SQLite、PostgreSQL 导出、向量索引、缓存、临时导出和备份；
- 任何能与真实个人、关系或一次具体思考过程重新关联的派生数据。

`privacy: shareable` 只表示内容具备被分享的候选资格，**不构成提交到软件仓库的授权**。公开作品需要一次独立、明确的发布操作，并进入专门的发布目的地，而不是 Arrive 软件仓库。

## 3. 物理布局

开发环境采用两个互不包含的目录：

```text
<software-repository>/       # Git 管理
├── backend/
├── docs/
├── templates/
├── scripts/
└── ...

<arrive-data>/               # 不使用 Git
├── raw/
├── inbox/
├── materials/
├── sources/
├── mirrors/
├── responses/
├── thought-maps/
├── drafts/
├── decisions/
├── outputs/
├── database/
└── exports/
```

数据根必须满足：

1. 不等于软件仓库，也不位于软件仓库的任何子目录；
2. 不通过符号链接、目录联接或挂载点重新出现在仓库内；
3. 自带 `.arrive-data-root` 标识和默认忽略全部内容的 `.gitignore`；
4. 不自行初始化为 Git 仓库；
5. 云同步、共享和备份必须作为单独的安全决定，不因其在本机而自动开启。

本机当前约定为：

```text
软件：D:\emotion
数据：D:\arrive-data
```

其他环境通过 `ARRIVE_DATA_DIR` 指定外部数据根。

## 4. 写入规则

所有接收真实内容的接口和任务都必须先取得数据根，再在数据根内构造路径。禁止以当前工作目录、源码文件位置或软件仓库相对路径作为运行数据落点。

SQLite 默认路径为：

```text
${ARRIVE_DATA_DIR}/database/arrive.db
```

显式设置 `ARRIVE_DATABASE_URL` 时同样执行边界校验；SQLite 文件必须解析到 `ARRIVE_DATA_DIR` 内，落在软件仓库或其他目录都会被拒绝。内存数据库和位于仓库外的测试临时目录不受底层测试引擎限制。

应用只会自动初始化不存在或为空的数据目录，并写入 `.arrive-data-root` 标识。已有内容但没有正确标识的目录会被拒绝，避免配置错误时把数据库写进无关位置。

未来新增文件存储、模型运行记录、搜索索引或附件处理时，也必须复用同一边界校验，不得另设仓库内缓存。

## 5. Git 防线

边界采用多层防护：

1. 根 `.gitignore` 忽略历史运行目录、数据库和本机环境文件；
2. `scripts/check_data_boundary.py` 检查 Git 索引的软件路径白名单、仓库内运行目录、SQLite 文件签名、实例记录 frontmatter 和 `ARRIVE_DATA_DIR`；
3. `.githooks/pre-commit` 在本地提交前执行检查；
4. GitHub Actions 在 push 和 pull request 上重复检查；
5. 后端在运行时拒绝仓库内的数据根和 SQLite 路径。

本地克隆后执行一次：

```powershell
git config core.hooksPath .githooks
```

这些技术措施不能识别任意文件中的全部语义。提交者仍需按第 2 节判断内容性质；不确定时一律按数据处理，先放在外部数据根。

## 6. 导出与发布

从私人数据生成可分享内容时，采用“导出而非搬回”原则：

1. 明确接收者、媒介、范围和隐私等级；
2. 从数据根生成一个待审阅导出；
3. 完成人工隐私、事实、署名和版权检查；
4. 获得一次针对该版本和该目的地的明确确认；
5. 发布到指定渠道，并在数据根记录发布事件。

一次发布授权不自动适用于后续版本、其他渠道或软件仓库。

## 7. 备份与删除

Git 不是数据备份方案。数据备份应使用单独位置，并根据内容敏感度采用设备加密或加密归档；备份的保留、恢复和删除策略与软件版本管理分开。

删除软件仓库当前版本中的文件不会删除 Git 历史。若数据曾被提交，需要先净化当前树，再经过明确授权执行历史重写和强制推送，并审计远端分支、标签、既有克隆和托管平台缓存。即使重写成功，也不能承诺已复制的数据从所有位置立即消失。

## 8. 评审清单

每次提交前确认：

- 文件是否只描述软件或通用协议；
- 测试内容是否完全虚构；
- 是否包含真实 URL、标题、原话、摘要、观点或时间线；
- 是否包含数据库、日志、缓存、导出或模型运行结果；
- 是否把 `shareable` 错当成 GitHub 授权；
- `python scripts/check_data_boundary.py` 是否通过。

任一项不确定，就不提交，并把内容移动到 `ARRIVE_DATA_DIR`。
