# Arrive 后端架构 v0.1

## 目标

后端的第一职责不是生成漂亮文本，而是可靠地保存思想形成和编码的过程，并把项目协议变成数据库可验证的不变量。

当前版本实现一个可运行的模块化单体。它适合早期快速验证；当来源抓取、模型推理和表达生成需要独立扩展时，再拆分后台任务与模型服务。

## 三阶段产品边界

| 阶段 | 后端职责 | 当前状态 |
| --- | --- | --- |
| 编码 | 把原始思考转换为可确认、可追溯的共享语义表示 | 已有数据基础，闭环待实现 |
| 传递 | 封装冻结版本并保证通道中的语境、来源、隐私与完整性 | 只规划数据契约 |
| 解码 | 根据具体接收者的知识、词义和思路生成适配表达 | 后续开发 |

当前后端中的素材、命题、来源、观点事件和思考地图属于编码基础设施，不代表编码引擎已经完成。接收者模型不进入当前纵向切片。

当前已确认的开发顺序进一步收窄为：先补齐忠实采集与镜像确认，再实现按需歧义检查与关键词语义确认，之后建立完整编码任务。协作机制阶段五至八暂缓。

## 技术选择

- Python 3.12
- FastAPI：REST API 与 OpenAPI 文档
- Pydantic：输入边界和跨字段验证
- SQLAlchemy 2：持久化抽象
- Alembic：数据库迁移
- SQLite：本地默认数据库
- PostgreSQL：后续多人和生产环境目标
- Pytest：领域行为和 API 验证

SQLite 只是本地默认值。模型没有依赖 SQLite 特有查询，但多写入者部署前需要把回应事件编号分配改为数据库序列或锁，并在 PostgreSQL 上验证迁移。

## 模块边界

```text
HTTP / OpenAPI
      ↓
Pydantic schemas
      ↓
Application services
      ↓
Domain invariants
      ↓
SQLAlchemy models
      ↓
SQLite / PostgreSQL
```

- `api.py`：HTTP 路由，不承载领域判断；
- `schemas.py`：外部输入、枚举和结构校验；
- `services.py`：编号、目标解析、追加事件和时间快照；
- `domain.py`：协议中的稳定词汇；
- `models.py`：数据库结构和唯一性约束；
- `serializers.py`：持久化对象到 API 表示的显式转换；
- `migrations/`：可审计的数据库演进历史。

## 核心数据模型

| 实体 | 稳定 ID | 作用 |
| --- | --- | --- |
| `Material` | `M001` | 保存原始思绪、感受、经历、矛盾或问题 |
| `Source` | `SRC-0001` | 保存外部来源身份与权利信息 |
| `SourceProposition` | `SRC-0001/P01` | 保存归属于来源的命题 |
| `PersonalProposition` | `P001` | 保存使用者明确采用或独立形成的命题 |
| `ResponseEvent` | `RSP-YYYYMMDD-NNN` | 追加共鸣、认同和采用变化 |
| `ThoughtMap` | `MAP-0001` | 保存命题、问题、概念、边界及其关系 |

现有 `Material` 能保存直接文字及其时间，但还不能表达多载体输入、来源定位批注或镜像状态。现有 `Source` 只保存一份档案引用，尚未建立可供长期定位的多版本来源快照。现有 `ThoughtMap` 也尚未强制镜像准入、关键词语义版本或依赖节点状态。

## 时间模型

带时间的素材与观点回应保存两份时间表示：

- 原始 ISO 8601 字符串：保留表达者提供的时区和时间形状；
- UTC epoch milliseconds：用于跨时区排序和 `as_of` 查询。

`recorded_at` 表示系统实际记录时间，`effective_at` 表示观点所属时间。二者分开后，可以在今天补录几年前的思想，而不会假装它今天才出现。

当前 `Material` API 在未提供 `effective_at` 时会回退到 `recorded_at`。下一纵向切片需要把“确认是当下”与“实际时间未知”分开：未知应保存为空及相应时间精度，思考地图只能把录入时间作为明确标注的展示回退，不能把它当成思想发生时间。

## 观点快照算法

共鸣、认同和采用是三条独立事件流。查询某个时间点的状态时：

1. 只选择 `effective_at <= as_of` 的事件；
2. 按有效时间、记录时间和内部 ID 排序；
3. 分别折叠三个维度；
4. `unspecified` 或 `undecided` 表示本次事件不修改该维度；
5. 返回每个维度的值、来源事件和生效时间。

因此，一次只更新“认同”的新事件不会意外清空此前的“共鸣”。

## 追加式历史

API 没有回应事件的更新和删除路由。观点变化通过创建新事件并填写 `supersedes` 表示。

数据库同时约束：

- 事件公开编号唯一；
- 同一天的事件序号唯一；
- `supersedes` 必须指向已有事件；
- 应用层要求新旧事件指向同一命题。

这不是完整的通用事件溯源系统，只对最需要保存变化的“观点回应”采用追加式模型。

## 来源与个人观点边界

来源命题不会因为使用者阅读或喜欢而自动成为个人命题。只有明确创建个人命题，或在 `adopt`、`adapt` 回应中提供个人命题文本，系统才建立 `P001` 等个人编号，并保存来源关系。

原始第三方全文不进入数据库。数据库只保存相对于 `ARRIVE_DATA_DIR` 且位于 `raw/` 下的存储键、字节数和 SHA-256；API 拒绝绝对路径与包含 `..` 的路径。实际全文、来源卡和数据库本身都位于软件仓库之外。

## 思考地图

思考地图允许保存矛盾，不要求形成树形结构。当前以经过验证的 JSON 节点和边存储，便于快速调整模型。应用层保证：

- 节点 ID 在单张图中唯一；
- 关系的两端必须存在；
- 不接受节点到自身的关系；
- `contradicts` 是一等关系，不会被自动消解。

当跨图查询和大型图遍历成为真实需求后，再将节点与边拆成关系表或图数据库；当前不提前引入复杂基础设施。

## 隐私与部署边界

当前 MVP 尚未实现账户认证、授权、字段级加密、审计日志和密钥管理，因此：

- 只在本机或受控的私有网络中运行；
- 所有真实运行数据写入仓库外的 `ARRIVE_DATA_DIR`；
- SQLite 必须位于该数据根内，数据根不得与软件仓库互相包含；
- 不得直接暴露到公网收集真实私人思绪；
- 不要把反向代理认证误认为完整的数据授权模型；
- 在实现多用户之前，所有表默认属于单一使用者。

进入可部署阶段前至少需要：

1. 用户和工作空间边界；
2. 每条记录的所有权与访问控制；
3. 静态和传输加密；
4. 敏感字段日志脱敏；
5. 数据导出、删除和保留策略；
6. 来源抓取的版权、robots 与失败处理策略；
7. PostgreSQL 并发和备份验证。

目录布局、Git 防线和独立发布流程见 [软件与数据隔离规范](./软件与数据隔离规范.md)。

## 模型服务边界

未来的大语言模型只作为“候选理解与候选表达”提供者，不能直接修改已确认命题。模型输出必须保存：

- 输入材料引用；
- 使用的提示或流程版本；
- 模型和配置版本；
- 输出时间；
- 内容类型：归纳、推测、问题或候选表达；
- 使用者确认状态。

模型提供者应通过接口适配，领域数据不绑定某一家服务。

## 下一纵向切片

下一阶段先实现“忠实采集与镜像确认”：

```text
外部来源 → SourceSnapshot → 定位批注 ┐
                                      ├→ Material → MirrorRevision
直接输入 ─────────────────────────────┘                   ↓
                                             使用者确认/纠正/拒绝
                                                        ↓
                                     可作为思考地图证据的确认素材
                                                        ↓
                                               进入语义检查切片
```

拟新增或扩展的领域对象包括：

- `SourceSnapshot`：不可变来源版本、抓取状态、时间、数据根相对键、哈希和字节数；
- `SourceAnchor`：全文、章节、段落、文本范围、页码、音视频时间段或画面区域的稳定定位；
- `Material.capture_mode`：区分直接输入与来源批注；`input_modality` 另行记录文字、音频、图片、文件或其他载体；
- `MirrorRevision`：LLM 的候选理解、素材引用、模型与提示版本；
- `MirrorConfirmationEvent`：追加式确认、纠正或拒绝事件。

原始输入到达时立即保存为待镜像状态，避免信息丢失；只有确认镜像或使用者确认的修正版具备作为证据进入正式思考地图的资格。来源原文不是个人素材，来源批注才是 `Material`。素材的当前准入状态可以作为查询缓存，但必须从追加式镜像确认事件推导。这些约束需要由数据库迁移、应用服务与 API 测试共同保证。

镜像流使用 `MIR-NNNN`，不可变版本使用 `MIR-NNNN/VNNN`，确认事件使用 `MCF-YYYYMMDD-NNN`。用户纠正会产生 `authored_by: user` 的新版本；拒绝某个 LLM 镜像不会删除或拒绝原始素材。

通用契约预留文字、音频、图片、视频和文档等输入载体及其数据根相对键、哈希、媒体类型和转写引用。第一个实现切片只交付文字直接输入与网络文章批注，其他载体通过后续适配器加入。

随后的纵向切片实现“按需歧义检查与关键词语义确认”。拟包含：

- `SemanticIssue`：锚定镜像版本和具体位置，记录歧义类型、影响对象、阻塞性与处理状态；
- `KeywordOccurrence`：把词面绑定到 `Material`、原句和精确位置，不按词面全局覆盖；
- `PersonalMeaningRevision`：带语境、适用范围、时间和 `supersedes` 的个人含义版本；
- `SharedSemanticAnchor`：独立保存共享解释的来源、领域、适用人群、共识状态和版本；
- `PersonalMeaningDelta`：记录个人含义与共享解释之间的相同、收窄、扩展、组合或冲突；
- `SemanticConfirmationEvent`：追加式保存单义、多义、当前特例、沿用旧义、确认未知、不需建模或延期结果。

关键词含义流使用 `TERM-NNNN`，不可变版本使用 `TERM-NNNN/VNNN`，语义确认事件使用 `SCF-YYYYMMDD-NNN`。镜像确认不自动确认词义；依赖尚未处理关键词的概念和命题保持待定，不能冻结进 `SemanticPacket`。确认多义、刻意模糊或目前未知属于已经处理，可以将明确的不确定性带入编码；`pending` 与 `deferred` 只阻塞依赖节点。

`TERM-NNNN` 是有语境和范围的含义流，不是词面的全局字典 ID。同词不同语境可以并行；同一含义演变才使用 `supersedes`。处理历史材料时保存 `contemporaneous` 或 `retrospective` 时间视角，避免把今天的解释倒填为过去含义。

上述语义切片完成后，再进入完整“编码任务”：`EncodingTask`、语义单元与关系、编码版本及 `SemanticPacket`。

`SemanticPacket` 成为编码、传递和解码之间的稳定契约。编码版本采用追加方式，避免候选归纳覆盖原始材料或已确认含义。接收者模型、接收者适配和理解反馈在编码闭环稳定后进入解码阶段。

这里的三阶段是领域职责边界，不强制对应服务部署顺序。若发送侧服务预先生成接收者适配文本，该转换仍由解码模块承担，随后才进入物理传输；传递模块自身不修改语义或做接收者适配。
